# /qa-payment — тестирование интеграции платёжного метода v0.1

> Скилл + суб-агент для Claude Code. Ведёт тестирование нового платёжного метода
> (провайдер / валюта / метод) от чтения задач до отчёта лиду: анализ MR,
> бережливый чек-лист по постоянным чек-листам лида, пошаговый живой прогон на
> DEV-стенде, синтетические подписанные вебхуки, итоговый коммент + аннотированный
> чек-лист + отчёт.

---

## Почему отдельный агент, а не общий impact-анализ

Интеграция платёжки — повторяющаяся задача одной формы, но с длинным живым
прогоном: несколько сессий, ожидание провайдера, подмена ключей, ретест после
фикса. Общий анализатор задачи выдаёт скоуп за один проход и раздувает число
тест-кейсов. Здесь наоборот:

- **основа чек-листа — постоянные чек-листы лида**, плюс только критичные дыры;
- **каждый пункт лида обязан попасть в покрытие** (TC / n/a / вопрос);
- **подозрение из кода ≠ баг** до подтверждения на стенде;
- состояние прогона живёт в трекере и переживает сессии.

## Как устроено

| Часть | Что делает |
|---|---|
| `.claude/agents/qa-payment-agent.md` | Разовый анализ: Jira [BE]+[FE] → оба MR → карточка метода, подозрения по каталогу классов багов, чек-лист JSON → HTML, план прогона, трекер |
| `.claude/skills/qa-payment/SKILL.md` | Фазы: intake/resume → анализ → живой прогон по одному шагу → синтетические хуки → итоговые результаты → предложения в базу |
| `workflow pay-hook` (`modules/payhook/`) | Печатает готовый curl подписанного вебхука провайдера. Сам ничего не шлёт, отказывается работать с хостами вне allow-list (защита от прода). Ключи берутся из конфига бэкенда на ветке MR в рантайме, на диск не пишутся |
| `config/qa-payment/` | База знаний: модель статусов, метод синтетики, каталог классов багов B1–B20, чек-листы лида, карточки провайдеров |

```
/qa-payment PAY-101 [PAY-102]   ← BE и/или FE задача; агент сам найдёт пару
/qa-payment PAY-101             ← трекер уже есть → продолжить с последнего шага
```

### Синтетические вебхуки

Провайдер на тестовом окружении часто не подтверждает платежи. Хуки шлём сами:

- **асимметричная подпись** (провайдер подписывает своим приватным ключом) —
  разработчик временно подменяет на DEV ключ проверки на ваш публичный; после
  прогона — вернуть обратно (скилл держит флаг в трекере и напоминает);
- **общий секрет** (MD5/HMAC по ключу из вашего конфига) — подмена не нужна.

Адаптер на провайдера — `modules/payhook/adapters/<provider>.py`
(`build_body / sign / verify / load_config`). В комплекте пример — HighHelp
(RSA SHA256). Новый адаптер пишется по разделу «Signing Spec», который агент
выписывает из MR.

## Установка

```bash
pip install -e ".[dev]"
cp config/example/jira/.env.example config/jira/.env        # заполнить
cp config/example/gitlab/.env.example config/gitlab/.env    # заполнить
cp config/example/payhook/.env.example config/payhook/.env  # DEV-хост(ы), repo бэкенда
cp config/example/projects.yaml.example config/projects.yaml
python3 -m pytest
```

Затем заполните под свой продукт:
- `config/qa-payment/payment-context.md` → «Repos», стенд;
- `config/qa-payment/lead-checklists.md` → чек-листы вашего лида.

Скопируйте `.claude/` в свой проект (или откройте этот репо в Claude Code) —
скилл `/qa-payment` и агент `qa-payment-agent` подхватятся.

## Правила, которые агент не нарушает

- GitLab и Jira — только чтение; запись в Jira — после превью и «да», под `JIRA_WRITE_ENABLED`.
- Ни одного вебхука без превью и явного «да»; только не-прод хосты.
- Шаги тест-кейсов — наблюдаемые действия (касса, админка, история баланса), без сырого SQL.
- Единицы сумм не пересчитываются молча — всегда оба значения.
- Проверка на проде после релиза — вне скоупа.
