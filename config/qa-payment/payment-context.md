# qa-payment — доменный контекст платёжных интеграций

> Шаблон: секции «Repos», «Как устроено у вас» и «Стенд» заполните под свой продукт.
> Модель статусов, принципы обработки, метод синтетики и каталог классов багов —
> общие, их можно оставить как стартовую базу (сверив со своим бэкендом).

Читается qa-payment-agent и скиллом /qa-payment целиком при старте.
Растёт после каждого метода: новые факты добавляются только после
подтверждения юзером (см. «Как пополнять»). Карточки провайдеров — в
`providers/<provider>.md`, чек-листы лида — в `lead-checklists.md`.

## 1. Форма задачи

## 2. Как устроено (пример типовой платформы — сверить со своей)

- Метод может регистрироваться миграцией **по бренду/витрине**.
  На аккаунте другого бренда метода нет — ожидаемо, первая причина «метода нет».
- Тип процесса метода: H2H / H2F (FE понимает только эти два).
- Лимиты метода задаются в админке; на DEV могут отличаться от Jira — это
  настройка, не баг. Бэк должен проверять лимиты сам до
  запроса провайдеру.
- Лимиты, зашитые в схему ручки (валидация схемы запроса) поверх админки, —
  исключение; обычно там «космические» значения, кратно выше админских. Если
  схема = админке → это факт для отчёта (max в админке не поднять), не баг.
- **Единицы суммы провайдеру — строго по его документации** (кто-то мажорные,
  кто-то минорные). Мы передаём то, что требует дока. В UI/админке — целые
  единицы. Никогда не пересчитывать молча: показывать оба значения.
- Вебхуки: `POST /api/webhook/<provider>/deposit|withdrawal` — без авторизации,
  защищены только подписью.
- Возврат игрока (`redirect_url`) — отдельно от callback-URL.
- Депозит пишет вейджер (x1 от суммы), дергает бонус-постхуки и реферальное событие.
- **Каскад/failover** — отдельный функционал, к интеграции метода не относится;
  в прогон метода не входит.

### Принципы обработки (со слов разработчика — общие для всех ПМ; пример, сверить со своим бэкендом)

- **Создание операции.** Провайдер в ответе на создание отдаёт id транзакции +
  метаданные (свои id, даты); статус если и есть — `processing`-подобный.
  Отмены в ответе на создание не бывает. **Финальный статус приходит только
  вебхуком.**
- **Провайдер не ответил нормально на создание** (таймаут, сеть, не-успешный
  код) → считаем, что оплата не создана, зарезервированные деньги возвращаем
  игроку. GET-сверки статуса нет (не все провайдеры её дают). Это дизайн, не
  подозрение. Баг — только когда **успешный** по доке ответ трактуется как
  сбой (класс B1).
- **Сумма депозита = фактически оплаченная**, а не заявленная. Пример: счёт на
  500, игрок перевёл 300 (одноразовый счёт, вернуть нельзя) → хук приходит на 500
  с отдельным полем фактической суммы 300 → зачисляем 300.
- **Перезапись статуса** — только если операция не в PAID. Деньги списаны
  (PAID), а провайдер шлёт другой статус → отвечаем ошибкой (дев: 500; на
  стенде реальный провайдерский адаптер дал 400 / OppositeFinalStatus). Вердикт — по статусу и
  балансу; фактический HTTP-код фиксировать в карточке провайдера.
- **Комиссия** считается в моменте операции (процент плавающий), пересчёта от
  хука в коде интеграции нет. Вывод: поле fee записи вывода; досчитывается
  отдельной фоновой задачей по расписанию (не часть MR интеграции) → отсутствие
  записи fee в MR вывода — не подозрение. Проверять fee после отработки задачи,
  через разработчика.
- **Споры (dispute):** провайдер может прислать хук «открыт спор», потом
  cancelled/paid и т.п. У нас почти нигде не обрабатывается — не TC, максимум
  строка «не обрабатывается» в карточке.
- **Поля хука `m_id`/`project_id`/`currency`** с конфигом/операцией не сверяем:
  по платёжке валюты X приходит только X. Дизайн.
- **Хук вывода на неизвестную операцию** → молчаливый 200 — нормально.

### Статусы
- `deposit_status_type`: PENDING, ENROLLED, CANCELLED, LESS_MIN, EXPIRED.
  ENROLLED = деньги зачислены.
- `withdrawal_status_type`: PENDING, PROCESSING, PAID, REJECTED, PS_REJECTED,
  ERROR, ERROR_PROCESSING, CANCELLED.
  - Одобрение в админке → PROCESSING → запрос провайдеру.
  - Хук вывода действует только на PROCESSING / ERROR_PROCESSING.
  - success → PAID (баланс не трогается, списан при заявке).
  - decline/error → PS_REJECTED + возврат на баланс (строка WITHDRAWAL REJECTED).
  - Провайдер не ответил нормально на создание → ERROR + возврат (WITHDRAWAL ERROR) — дизайн.
  - Повтор того же финального статуса → тихий выход, без второго возврата.
  - PAID + другой статус → ошибка (см. «Перезапись статуса»), PAID и баланс не трогаются.
- История баланса игрока (WITHDRAWAL / WITHDRAWAL ERROR / WITHDRAWAL REJECTED /
  DEPOSIT) — главное доказательство денежных багов.

## 3. DEV-стенд (наблюдения с реального прогона — сверить со своим)

- Стенд: `<dev-host>` (касса), админка `<dev-admin-host>`.
- **Ключи провайдеров на DEV — только dev-ключи или прод-ключи, выданные под
  дев-тесты** (политика: настоящих прод-ключей у нас нет физически). Реальных
  выплат с DEV не бывает — одобрять выводы на DEV можно, вопрос «не уйдут ли
  настоящие деньги» не задавать. Отсутствие песочницы у провайдера — не риск.
- **env-переопределений конфига на DEV нет** → ключи/настройки = `config/default.yaml`
  на ветке MR. Не спрашивать.
- Grafana (qa-logs) и БД (qa-database) смотрят только в **прод** — на DEV не
  помогают. Источник правды на DEV: логи депозита/вывода в админке
  (`CREATE_DEPOSIT`, `CREATE_DEPOSIT_PARAMS`, `WEBHOOK`), статус, баланс,
  история баланса, тултип ошибки вывода.
- Отклонённый (битая подпись) хук тоже может попасть в логи как WEBHOOK — судить
  по статусу и балансу, не по наличию записи.
- **Финальный статус органически:** идём в ТГ-чат провайдера и просим прислать
  хук об успехе/отказе депозита/вывода по id транзакции — основной путь.
  Провайдер не отвечает / без реквизитов («Requisites not found») → синтетика.
- Ошибка вывода на DEV — не «шум дева»: читать тултип (так найден реальный Critical-баг).
- Баланс для выводов — начислением в админке, не mock-депозитами.
- Одновременно у юзера один висящий вывод → выводы последовательно.
- Лимиты в обход формы: «Copy as cURL» запроса кассы из DevTools, JWT живёт
  минуты — отправлять сразу. Значения > int32 упираются в общую валидацию поля,
  а не в лимит метода.
- Комиссия видна, вероятно, только в БД → на DEV проверка через разработчика.

## 4. Синтетические хуки (метод лида)

Органика через ТГ-чат провайдера (§3) — первая попытка для успеха/отказа.
Синтетика — для негативов и повторов (битая подпись, повтор финального,
поздний противоположный статус, неизвестная операция) и когда провайдер не
шлёт хуки.

1. Провайдер с асимметричной подписью проверяет хук **своим** публичным ключом.
   Разработчик временно подменяет на DEV ключ проверки на **наш** публичный.
2. `workflow pay-hook <provider> …` — подписывает ключом из конфига MR-ветки
   (ключи не на диске), печатает curl + `local verify OK`.
3. Отправка — только после превью и «да» юзера, только DEV-хост.
4. Пока ключ подменён, настоящие хуки провайдера на DEV отбиваются (400) →
   органику через ТГ-чат в это время не ждать; в конце **всегда** попросить
   разработчика вернуть ключ; флаг в трекере.
5. Провайдер без адаптера → адаптер пишется по Signing Spec агента
   (инфраструктурная задача) до первого хука.
6. **Общий секрет** (MD5/HMAC по ключу из нашего конфига) —
   подмена ключа НЕ нужна: подписываем тем же ключом, которым бэк проверяет.
   Пункты 1 и 4 не применяются, органика и синтетика работают одновременно.

## 7. Прод-проверка после релиза (памятка — не фаза агента)

Сам прогон на проде вне скоупа агента и скилла. Эта памятка выдаётся юзеру в
конце P4 и служит опорой, когда юзер приходит с прод-транзакциями (через
`/qa-logs`, Grafana default = прод). Источник: первый реальный релиз метода.

**Проверка логов:** по запросу юзера скилл гоняет `qa-logs-agent` (P6 в SKILL): A — конкретные id, B — свип всех игроков провайдера с момента релиза/смены ключей (коды ответов, ошибки подписи, причины decline, дубли финалов, зависшие промежуточные). Дубль success → предложить `qa-database-agent` (прод-БД) на «начислено ровно раз».

**Порядок:** релиз → 2 тестовые заявки на проде (одна → success, вторая →
decline) → в ТГ-чате провайдера просим проставить статусы → в прод-Grafana
проверяем, что все КБ получили 200 → в админке статус + баланс + история
баланса. Каждая проверка — только по заявкам, созданным **после** последнего
изменения конфига (ключи/URL).

**Как читать сигналы:**
- **«Колбэки не доставлены» от провайдера = мы ответили не-2xx.** Сначала
  смотрим в прод-Grafana коды ответов по этим id, потом подозреваем код.
  Типичная причина на старте — неверные ключи провайдера → массовый 400 по
  подписи. Провайдер может не повторять часть статусов (у одного провайдера
  `processing`/`decline` — один раз, `dispute`/`success` — с ретраями): такие
  КБ навсегда остаются «недоставленными», хотя после фикса всё ок.
- **После смены ключей проблема по старой заявке — не регрессия.** Заявка,
  созданная до фикса, может отбиться и после него.
- **Строка WEBHOOK в логе пишется до проверки подписи** (и на проде) — судить
  по коду ответа / статусу / балансу.
- **Антифрод провайдера режет тестовые прод-платежи** (decline с текстом вроде
  «Anti-fraud declined»). Это вердикт провайдера, не наш дефект. Тест — без
  VPN, с реальным IP страны метода, без серии попыток подряд.
- **Повторный success** на проде бывает → обязательная проверка: баланс
  начислен ровно один раз (история баланса — одна строка DEPOSIT).
- Время жизни заявки (`lifetime` и т.п. в хуке) отличает истечение от отказа.
- В админке, колонка Transaction ID: крупный id — `request_id` провайдера,
  мелкий над ним — наш `payment_id`. Оба нужны для поиска в Grafana и для ТГ.

**Сообщения в ТГ-чат провайдера** (от лица юзера, нейтрально, без упоминания
ИИ; id — полные, не обрезанные; время — с часовым поясом):

1. Проставить статус тестовой заявке:
   > Добрый день! Мы провели релиз <метод/валюта> и делаем тестовые платежи на проде. Просим перевести заявки в нужный статус:
   > • `<request_id>` (наш id `<payment_id>`), <сумма> <валюта>, создана <ЧЧ:ММ UTC> — **success**
   > • `<request_id>` (наш id `<payment_id>`), <сумма> <валюта>, создана <ЧЧ:ММ UTC> — **decline**
   > Спасибо!

2. Ответ на «колбэки не доставляются» (после проверки в Grafana):
   > Проверили на своей стороне: колбэки по заявкам `<id…>` до <ЧЧ:ММ UTC> отклонялись из-за неверной подписи — ключи были заменены в <ЧЧ:ММ UTC>. После замены все колбэки принимаются с ответом 200 (последние: `<id>` <статус> <время>). Можно возобновлять трафик / пришлите, пожалуйста, повторно колбэки по `<id…>`, если это возможно.

3. Отказ антифродом:
   > По заявкам `<request_id>` и `<request_id>` (<время UTC>) пришёл decline «<текст причины>». Это наши тестовые платежи. Подскажите, пожалуйста, какое правило сработало и что нужно изменить, чтобы тестовый платёж прошёл?

4. Заявка зависла в промежуточном статусе (dispute / processing):
   > Заявка `<request_id>` (наш id `<payment_id>`, <сумма>, создана <время UTC>) остановилась в статусе `<статус>`, финального колбэка не было. Подскажите, пожалуйста, её итоговый статус и пришлите финальный колбэк.

Ответы провайдера и найденные особенности → в `providers/<provider>.md`
(раздел «Прод») через P5.
