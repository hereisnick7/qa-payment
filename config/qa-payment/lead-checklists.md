# Чек-листы лида — основа каждого прогона платёжного метода

> Шаблон: замените на постоянные чек-листы вашего лида. Ниже — реальные
> списки, с которых агент строился, как пример формы.

Оба списка обязательны для КАЖДОГО метода. Каждый пункт обязан попасть в
покрытие (`Coverage` в чек-листе и в трекере): TC, «не применимо (почему)» или
«вопрос (кому)». Молча выпавший пункт = дефект прогона (первый реальный прогон
потерял L2-2, L2-3, L2-6 именно так).

## L1 — флоу лида

| ID | Пункт |
|---|---|
| L1-1 | Пройти флоу депозита: успешный + неуспешный |
| L1-2 | Включить платёжку в админке, проверить на фронте |
| L1-3 | Отправить реквест от нас провайдеру |
| L1-4 | Автоапрув либо номер транзакции в ТГ-чат с провайдером → попросить нужный статус |
| L1-5 | Проверить, что реквест ушёл корректно |
| L1-6 | Проверить лимиты |
| L1-7 | Проверить, что колбэк от провайдера дошёл и обработался |
| L1-8 | Проверить, что статус депозита сменился |

## L2 — «Чеклист по платежке»

| ID | Пункт | Заметка |
|---|---|---|
| L2-1 | После вебхука сумма меняется на указанную в вебхуке | |
| L2-2 | Комиссия после пересчёта в п2п меняется | Пример заметки: «в коде интеграции пересчёта нет, fee считается в моменте; досчёт — фоновая задача по расписанию → проверка через разработчика после её отработки, иначе `n/a (пересчёт вне MR интеграции)`» |
| L2-3 | Комиссия в БД устанавливается только по нашему значению, не из вебхука | Комиссия видна вероятно только в БД; без доступа к БД стенда → шаг через разработчика. Какая комиссия куда пишется (наша / провайдерская) — до эталона это вопрос |
| L2-4 | Если пришёл успех после фейла — статус меняется | |
| L2-5 | Прислали на депозит успех после фейла — что будет | |
| L2-6 | Прислали на вывод успех после фейла — что будет | Ожидаемое поведение не зафиксировано → вопрос разработчикам, пока не ответили |

## Эталоны, уже согласованные с лидом (не переспрашивать)

Заполняется по ходу прогонов: ответ лида/разработчика на поведенческий вопрос →
строка сюда, с датой и провайдером. Пример формы:

- Сумма из success-хука перезаписывает сумму депозита, лимиты повторно не проверяются — корректно (<провайдер>, <дата>).
- CANCELLED-депозит оживает поздним success → зачислен — корректно (<провайдер>, <дата>).

## Эталоны от разработчика (общие для всех ПМ — не переспрашивать)

Полный текст — `payment-context.md` §2 «Принципы обработки» и §3. Пример формы
(так выглядел этот блок после первого раунда ответов разработчика — замените
своими ответами):
- Прод-ключей на DEV нет (политика) → реальных выплат с DEV нет; успех/отказ — хук по просьбе в ТГ-чате провайдера.
- env-переопределений конфига на DEV нет.
- Ответ создания: id + метаданные, отмены не бывает; финал — только вебхуком.
- Не-нормальный ответ на создание → «не создано» + возврат резерва; GET-сверки нет.
- Зачисляется фактически оплаченная сумма, не заявленная.
- Статус не перезаписывается из PAID; PAID + другой статус → ошибка.
- Комиссия — в моменте, пересчёта от хука нет; fee вывода досчитывает фоновая задача.
- Каскад — вне скоупа; m_id/currency хука не сверяются; хук вывода на неизвестный id → 200 — ок; единицы — по доке провайдера; лимиты в схеме ручки — исключение.
